# dsh-sidebar-narrator · 侧写

> 包名 `dsh-sidekick-lens`（插件 id、`set_plugin` 的目标都用它），GitHub 仓库叫 `dsh-sidebar-narrator`。

右侧栏里的三行话：**它干完什么、在干什么、下一步干什么**。

DSH 工作的时候，主对话在滚，工具日志在刷，你根本看不出来它到底在干哪一步。这个插件不给你第二块聊天屏，只给你三行字、一盏灯、一个位置感，点开才看细节。

## 它是什么

原生右侧栏 tab（`ctx.sidebarRightTabs` + `sidebar.right.pane.tab` 座位），和文件预览、终端并排、可拖拽合并，宽度不够时只收缩自己的文案，不横向溢出。

三行之后是**总览**，再往后才是它的证据层：

| 那一块 | 回答的问题 | 为什么不能省 |
| --- | --- | --- |
| **从开头到现在** | 「这一整场从头到尾，办成了什么、卡在哪」 | **这是主视图**。每件你提的事就是一**章**：问了什么 → 发生了什么 → 怎么收尾。没有这条主轴，面板只是一串无主的孤句，读者得自己拼出「这句属于哪件事、那件事后来怎样了」 |
| **派出去的队** | 「我手下还有谁在干活、各自到哪了」 | 一个子 agent 是**一整支队伍**，不是一次工具调用。以前面板只显示「派了个小助手去」，指挥官看着一个兵，管这叫全局 |
| **清单对位** | 「它定的计划推进到哪了」 | 计划写完就没人对账，那就是一张愿望清单。每条现在带状态：做完了 / 正在做 / 还没动 / 不做了 |
| **战况** | 「刚才到底发生了什么」 | 编年史说「这件事成没成」，战况说「那一分钟它具体做了什么」。**证据层**，需要时再展开 |

### 为什么是「一件事一章」

早期版本把战况做成一串扁平条目，用户的原话是「片段展现，读起来没头没尾，可读性极差」。诊断下来是结构问题，不是措辞问题：

- `recordRequest()` 过去在用户一开口时，就把上一件事**整个丢掉**，只留一个 `closedBy` 标记。43 件事只有最后 1 件活着 —— 面板想讲全局，手上却只有一段。
- 每一条战报都是**无主句**：「版本整理好了」「那一步没做成」。它属于哪件事、那件事最后成了没有，全都不在行里。

现在每件事都被**收起来**（`history`，最多 60 件），并且自带三个端点：**开头**是用户的请求原话，**中段**是压缩后的关键动作（动手 / 失败 / 验证），**结尾**是一句结论加一句收尾语。正在进行的那件事也占一章，所以「当下」不会缺席。

一句话总账在最上面：`2 件办完 · 1 件没过验证 · 1 件还开着`。指挥官第一眼要的是这个，不是哪一章。

总账仍然是**提炼总账**，回答的是另一个问题：三行说「最近一步做了什么」，账本说「你让我办的那件事推到哪了、产出什么、还差什么、它自己说接下来做什么」。

它的信息结构是刻意定死的，**先说结果，再说缺口**：

1. **做成了什么** —— 数字给范围，名字给落点：`动了 4 个文件（说明文档、客户端）`。
2. **还差什么** —— 清单上没打勾的那几件，并且点出下一件是哪个：`还剩 3 件，下一件是「跑测试」`。

它**刻意不先说**「看过 29 处代码、跑过 25 次命令」。这类计数只证明它在忙，回答的是「它移动了多少」，而不是「我离想要的东西近了多少」。这些数字仍然留在展开详情里，谁想看都能看到，但一句话的摘要只留给结果和剩余工作。

> 这条规则的依据是 [Progress Ledger](https://agentic-ux.com/patterns/progress-ledger) 的「IDE agent 的总账该读起来像 changelog，不是 debug log」与 [Return Moment](https://agentic-ux.com/patterns/return-moment) 的「先讲结果和范围，不要回放每一次工具调用」。早期版本正是这两个反面的例子：70 步之后只说「改了 3 个文件、看过 29 处代码、跑过 25 次命令」，用户看完仍然不知道这事办到哪了。

**做完了什么 / 还剩什么 / 接下来做什么，只有模型自己的正文说得出来。** 工具调用只会说「读了哪个文件、改了哪一处」——它证明活干了，但永远不说「你要的那个东西现在怎么样了」。所以面板除了工具事件，还读 `assistant/message` 的正文：抓「做完了什么」的陈述（`PROSE_DONE`）、「还剩几个问题」这类状态（`PROSE_STATUS`）、「接下来…」的计划（`PROSE_PLAN`）和它自己列的清单（`PROSE_ITEM`）。在一条真实会话的 43 件请求里，53% 有做完陈述、72% 有下一步、40% 自己列了清单——这些以前全被丢掉，面板只能拿工具事件套模板，于是总结永远像废话。

这类行的来源标 **仅据汇报**（是它说的，没人核对过），而工具那句降到展开层的「看到了什么」当证据。计划超过 120 步、或跨过了一个新请求就作废——三百步前写下的计划是另一件活。它自己列的清单会渲染成账本里的「接下来这些」，不是替它重排一份。

有总结句时就不再单列计数，同一件事不说两遍。「下一步」优先取清单上的下一件；没有清单时，会优先引用 agent 自己刚说的那句打算（标为**仅据汇报**），而不是套模板句。

每条都能点开，看四件事：**为什么做 / 看到了什么 / 结果是什么 / 可以怎么调整**。

每条还标着来源：

| 标记 | 含义 |
| --- | --- |
| **已观察到** | 真读到了工具调用和工具结果，这话是事实 |
| **推出来的** | 没有直接证据，是按刚做完那一步的类别推的下一步 |
| **仅据汇报** | 只有主 agent 自己这么说，没人核对过 |

第三种标记是补的，不是装饰。「下一步」这一行大多数时候本来就没有证据可依 —— 它只能按上一步是读是写、是什么动词来猜。以前这类行全部标「已观察到」，真会话里 99.1% 的下一步都这么标，徽标本身就变成了空话。现在只有三种情况标「已观察到」：清单上真排着的那一件、刚读到的工具结果、正在跑的那个调用（实测 4460 帧里 72 帧，占 1.6%）。着色规则不变：只有「仅据汇报」用琥珀色，「推出来的」用一圈细描边，不引入第三种颜色。

三行和账本不是两套逻辑：`buildStory()` 先把事件折叠成一份「这件事到哪了」的记录（做成了什么、还差什么、手上正干着什么、下一步该是什么），三行是它的前三句，账本就是它的一句话摘要。所以它们永远说同一件事，不会一个说「等结果」、另一个说「下一件是补边界测试」。

## 三条介入通道（视觉上是三个不同的东西，不是一个输入框）

### 1. 问解释助手 —— 只读，不碰主 agent

单独调一次模型，只喂给它步骤摘要（已经剥掉工具名和路径）。

- **不发消息**给主 agent
- **不进**主对话上下文
- **不改变**执行路径

适合问：「这一步为什么这么做？」「它是不是卡住了？」「还有哪几件事没做？」

实现上：宿主自己 `llm.stream(...)`，**不带 sessionId、不带 tools、不带 toolHistory**，和主 agent 循环彻底隔离。

提示词在 `lib/narrative.js` 的 `explainPrompt(digest)` 里，是个纯函数（便于测试）。全文：

```text
你是一个坐在用户旁边的“侧边旁白”。你的唯一工作，是用大白话给用户解说主 Agent 此时此刻在干嘛。用户可能完全不懂代码，你要让他觉得安心、听得懂。

请严格遵循以下要求：
1. 只说 1 到 2 句话，口语化，像朋友在旁边提示。绝对不要用任何 Markdown 格式、列表、或者标题。
2. 把机器动作翻译成“生活化动作 + 业务对象 + 目的”。
   - 错误示范：“正在调用 read_file 查看 src/auth/login.tsx，并读取第 40 行参数。”（太机器）
   - 错误示范：“它在翻文件，然后在改配置。”（太模糊）
   - 正确示范：“在看登录页的代码，确认输错密码时往哪跳。看完应该就会去改配置了。”
3. 屏蔽底层技术细节（如代码函数名、命令行参数、绝对路径），但允许保留业务相关的名字（如“登录页”、“测试”、“配置文件”）。
4. 只依据下方【当前进展】里的事实来说。如果信息太少看不出来，就说“这会儿它还在默默干活，暂时看不出具体在忙啥”，绝对不要瞎猜编造。
5. 不要用“根据记录”、“综上”、“目前正在执行”这种公文腔，也不要说“我会帮你转告”，你只是个旁白。

【当前进展】（这是你唯一能看到的信息）：
<digest>
{digest}
</digest>
```

`{digest}` 是运行时拼的观察记录，分两段，因为面板对用户的承诺是「每条结论都标来源」，
摘要如果混成一段，模型就没法兑现这个承诺：

```text
【已观察到】（真的读到了工具调用和结果）
状态：正在跑（验证结果）
到目前为止：动了 4 个文件（说明文档、客户端），清单 2 / 5，还剩 3 件，下一件是「跑测试」。
还没做完：跑测试；补边界情况；更新说明
最近一次动作：刚刚
当前动作：在跑测试，确认改完没有碰坏别的。
它下一步大概会：把结果对一遍，再决定接着改哪里。（推测）
已完成步骤数：58
清单进度：3 / 5
- 看完了相关代码。
- 改完了「客户端」。
清单未完成：补 README；跑回归测试
动过的文件：说明文档、客户端、语言层、宿主半
你最近给的提醒：那个文件先别改

【仅据汇报】（只有它自己的说法，没有工具证据）
它自己最后说：三条路子都验过了。
它心里正在盘算：（它当下的思考原文，工具名与路径已换成中性说法）
```

注意「它下一步大概会」带 `（推测）`——那是推断，不是观察，不标出来模型就会当事实转述。

**什么时候展示**：全部由事件驱动，没有轮询。

| 事件 | 行为 |
| --- | --- |
| `turn/start`、`turn/end`、`tool/result` | 立即算一帧推给面板 |
| 其它 `session/event`、`agent/assistant-stream` | 350ms 节流后再算 |
| `agent/status`、`agent/error` | 立即推 |

推之前会比对 `signatureOf(view)`，一模一样就不推——面板不会因为 agent 在吐字而每 350ms 重画一次。

**什么时候总结**：`summary` 不是定期生成的，是每次算帧时从 `tally`（按动作类别的累计次数）、
`files`（动过的文件）、`failedCount`、`todos` 现算的，所以它永远和当前状态一致，不会落后一段。

### 2. 告诉 Agent —— 软介入，不打断当前步骤

标签写得很直白：**告诉 Agent（不打断当前步骤）**。

走 `agent.steer(message)`：消息进 `next-step` 信箱槽，当前正在跑的工具调用照常跑完，**下一个 step 边界**才被读取。

已经完成的工作全部保留。

### 3. 先停一下 —— 硬打断，但把代价讲清楚

两步确认，确认框上写着：

> 打断后已完成的内容会保留，它会说明中止了什么。

走 `agent.cancel({ kind: 'user' }, { keepInbox: true })`：立刻中止当前 turn，但队列里的东西不丢。

停完面板会回一句话：**保留了什么、中止了什么、建议下一步**。

## 安装

插件是标准的 DSH bundle。源码目录：`D:\work\tagclear\dsh-sidekick-lens`；
GitHub：<https://github.com/gcwarmman/dsh-sidebar-narrator>（包名仍是 `dsh-sidekick-lens`）。

**你现在这台上已经装好了**，不用再装。下面这段是给「换一台机器」或「别人想装」用的。

```bash
# 从 GitHub 装（推荐，别人用这条）
dsh plugin --profile web add github:gcwarmman/dsh-sidebar-narrator

# 或者用预构建包装（不需要构建授权，比从源码装更省事）
dsh plugin --profile web add https://github.com/gcwarmman/dsh-sidebar-narrator/releases/latest/download/dsh-sidekick-lens.tgz

# 或者从本地目录装
plugin_manager action=install_bundle target="D:\work\tagclear\dsh-sidekick-lens"
```

装完刷新页面（`http://127.0.0.1:3080`），右侧栏的引导页会出现「侧写」这一项；因为这是唯一条目，它会直接自动打开。

> 装完如果没出现，先看 `plugin_manager action=list_plugins` 的输出里有没有 `dsh-sidekick-lens`，再看 `warnings`。

### 别人怎么装

三种形态，按「对方有多怕麻烦」排序：


改完代码要让它重新加载：

```bash
plugin_manager action=set_plugin target=include:sidekick-lens enabled=false
plugin_manager action=set_plugin target=include:sidekick-lens enabled=true
```

> `dsh plugin ...` 只是把参数原样转给 profile 目录里的 pnpm，所以 `add` / `remove` / `why` 都能用。
> 装 B/C 形态时 `plugin_manager` 会跑一次 pnpm 链接，并打出一大片**既有的** peer-dependency 警告墙
> （`dsh-better-sidebar`、`dsh-mnemon`、`@nanmicoder/dsh-agent-teams` 等），那与本插件无关。

### 视觉：一张安静的卡片

面板就长在宿主主题里，不另起一套视觉语言：底色用 `--dsw-alias-bg-layer-1`，文字用 `--dsw-alias-label-primary/secondary/caption`，
浅色主题自动跟随。没有星野、没有极光、没有反应堆核心——那些试过，在 176–284px 的侧栏里只剩噪音。

留下的规则：

1. **一个强调色跟着灯走**。根节点带 `data-light`，派生 `--skl-accent`（蓝 `#5b8fd0` / 黄 `#c08b3e` / 青 `#3f9c94`；绿红直接取主题的成功/报错色）。灯、「正在做」行、三张门的标题都靠它级联，改一个属性整屏换色。
2. **没有边框，只有发丝线**。行与行、段与段之间是 8%（`--skl-hair`）与 15%（`--skl-hair-2`）的透明细线，不是盒子。
3. **只留两处动画，都携带信息**：灯的呼吸 `skl-breathe 2.6s`（在跑时才呼吸，说明它还在采样）与心跳波形（真实事件打点，静默时压平）。装饰性动效全部删掉了。
4. **来源徽标是纯文字**：`已观察到` / `推出来的` / `仅据汇报`，只有后者用琥珀色 `#c9a26a`，全 panel 唯一的第二种颜色；`推出来的` 用一圈 14% 的细描边，不加颜色。
5. **位置感不用进度条**。`.skl-progress` 节点还在但 `display:none`；位置只靠头部「第 N / M 件」，单位是**用户提的事**，不是工具调用。43 件请求配 2244 次工具调用，按调用数报「第 49 / 50 步」读者学不到任何关于进度的事。
6. **头部三件事：状态词、已用多久、第几件**。状态词在「等你回话」时换掉（灯仍是青色，不新增第六种颜色）；耗时只在干活与等人时显示，客户端拿 `elapsedMs` 加本地时差自己数，所以两帧之间它也在走 —— 参考 assistant-ui 的 `AgentStatus`（`state dot + label + elapsed`，`done` 之后不再计时）。
7. **窄栏靠容器查询，不靠媒体查询**（见下一节）。

`prefers-reduced-motion: reduce` 下动画全部关掉。

### 窄栏：面板问自己有多宽

侧栏会和终端、diff 分栏，最窄时只有 **176px**。硬按视口写媒体查询是错的——viewport 1264px，面板只有 176px。
所以 `.skl` 声明 `container-type: inline-size`，用 `@container (max-width: 215px)` 改版式：标签与徽标提到第一行（标签居左、徽标靠右），正文独占整行，详情字段名也从左侧栏改成上方标题。

实测（真 GUI 分栏态，`.skl` 宽 176px）：三行高 63 / 61 / 78px，三行正文 `scrollWidth - clientWidth = 0`，`panelScrollX = 0`，`bodyScrollX = 0`。
改造前同一宽度下「已完成」行会折成「看完了相关代 / 码。」这种断法。

| 空状态**最后一句**引用的是 markdown 骨架与引子：`最后一句：## 这次修掉的真问题 **1. 英文调试文本漏进面板**`、以冒号收尾 | 回复按原文截取，`##`/`**`/目录树/「下面列一下：」全被当成结论；截头还专挑开头的「汇报一下：」 | 先按行剥 markdown 再 `scrub`（顺序反了 `^` 锚点就认不出标题）；`plainText()` 只取以句号收尾的整句，跳过「下面/以下/先说」这类引子；整句都太长时退到最后一个逗号，宁可不说也不留半个句子 |

| **正在做**带着同一批固定评注收尾：`在找下一处要动的地方` / `在挑下一处该看的地方` / `在判断要不要接着改`（41.1% 的帧） | 句尾从 `BETWEEN_STEPS` 按 kind 取常量，读者得不到任何新信息 | 删掉两张常量表，句尾改成**距离上一步多久**（「这步收尾了，已经 4 分钟没有新动作」）——「在干活」与「卡住了」的区别就在这个数字上 |

| **进度数的是工具调用，不是用户提的事**（43 件请求 / 2244 次调用，刻度报「第 49 / 50 步」） | `position` 的分子分母都取 `stepsDone` 与 `pending`；`user/message` 只被当作「提醒」存进 `steers`，从没被当成一件事记下来 | 新增 `request` 状态：用户每开口一次就记一件（`recordRequest`），工具结果按这件事归账（`noteInRequest`）；`buildRequest()` 只从证据出发判定 `looking / changed / verified / blocked / done` 四态，`position` 改成「第 N / M 件」；总账开头直接说「你提的第 N 件…改了什么、验没验、还差什么」 |
| **改完就算做完了**，没人问「改完之后跑过没有」 | 只要 `writes > 0` 就认为有产出，跑没跑过、跑过的那次碰没碰改动都不影响结论 | 记 `lastWriteAt` 与 `lastRun`，只有「改动之后的成功运行」才算 `verified`；`changed-unverified`（改了没验）与 `blocked`（验了没过）分开说，`open` 字段直接给出「还差什么」 |
| **清单冒充进度** | `pendingTodo` 一有值就占住「下一步」，而清单可能 2200 步前写过就没再更新 | 清单超过 40 步未更新即判定陈旧（`todosAreFresh`），不再被当作「下一件」；`position` 用请求数，清单只作 `progress.todos` 的附带信息 |
| **「等你回话」和「在跑或测」共用一盏灯**，看不出它是停下来等你 | `lightOf()` 把 `ask` 归进 `cyan`，状态词也就跟着说「在跑或测」 | 新增 `view.status` 四态（`working / waiting / done / failed`）；`ask` 在飞时报 `waiting`，状态词换成「等你回话」，**灯色不新增**（仍青），参考 assistant-ui 的 `AgentStatus` |
| 头部只有「第 N / M 件」，**看不出这事干了多久** | `elapsedMs` 早在 `buildView` 里算好，客户端从没渲染它 | 头部加 `.skl-elapsed`：只在干活/等人时显示，客户端用 `elapsedMs + (Date.now() - updatedAt)` 自己数，两帧之间也走；`done` 之后隐藏 |
| **总结全是套话**：`动了 N 个文件，清单过期，碰过 N 次错` | 只读工具事件。工具只会说「读了/改了什么」，从不说「你要的东西怎么样了」；「做完了什么 / 还剩什么 / 接下来做什么」只存在于模型自己写的正文里 | 新增 `prose`：从 `assistant/message` 的正文里抓做完（`PROSE_DONE`）/ 下一步（`PROSE_PLAN`）/ 枚举清单（`PROSE_ITEM`）；实测 43 件请求里 53% 有做完陈述、72% 有下一步、40% 有清单。`buildSummary` 与「下一个」行优先引用它，来源标 `reported` |
| 「已完成」说的是**它翻了哪个文件**，不是**做成了什么** | `doneRow()` 只从工具调用拼句子 | 同一条 `prose.done` 优先，工具那句降到展开层的「看到了什么」当证据 |
| **还剩两个问题：…** 被当成「下一步」整条丢掉 | `PROSE_PLAN` 把它当计划捕获，却没地方法显示状态 | 单拆 `PROSE_STATUS`（还剩/还差/剩下/问题/已知）：它是工作状态，进「已完成」，不是下一步 |
| 总结以**冒号收尾**：`接下来重新加载并到真实页面上检查：。` | `buildSummary` 直接贴 `prose.plan` 原文，而原文在引出清单 | 统一走 `planLine()`：含「：」就截到冒号前，剥掉「接下来」前缀与尾标点 |
| 面板承诺的计划**看不见** | `checklist` 已经进了 `view`，客户端 `Ledger` 从没渲染 | `Ledger` 加 `.skl-plan` 段（小标题 + 逐条），用既有颜色变量，不新增颜色 |
| 三百步前的计划**还在当下一步** | `prose` 一直留着，跨请求不失效 | `proseFresh()`：早于当前请求、或超过 120 步就作废；`recordRequest` 直接清空 |
| 战报里**失败那行写着「跑完测试了。」** | 失败行复用了「已完成」那一套过去式动词，把一次失败拼成了一句庆祝 | 失败走 `failureText()`（「…那一步没做成：<原因>」），不走 `sentence()`；断言失败行不得匹配 `跑完了/做完了/改完了` |
| 战报里**「版本整理好了」连着出现六条**（一场十七格里九格是重复） | 去重只比字面相等，同一个动作换了个对象名就算新的一行 | `sameBeat()` 先把「」里的对象剥掉再比，同一动作合并并把时间挪到最新，另记 `count`；单次不显示次数，重复才显示 `×N` |

| 重载后**面板停在旧画面上**，子队跑完了父面板不动 | 子会话的状态变化只推送它自己，父会话的树没人重算 | `publishUp()`：子会话一有动静就顺带刷新它的父会话；`signatureOf` 把 `tree` 与时间线尾也算进签名 |
| 「派了个小助手去」**就是全部的子队信息** | 只处理 `session/event` 里主队的 id，子会话被当成一次工具调用 | 所有 live session 都折叠（`{global:true}` 本来就收到了），父子关系从子会话自己的 `session.header.parentSession` 读，谁的日志先到都不影响 |
| 战况在 **176px 分栏下横向溢出 3px**（README 曾写「实测 0」，实际不为 0） | `.skl-row` 是 `width:100%` 加左右 `padding`，默认 `content-box` 会超出内宽 12px | 给 `.skl-row` 加 `box-sizing: border-box`；实测 176/220/260/300/360/460 六档 `panelScrollX = 0` |

| 提醒发出去之后**没有任何下文**，分不清它采纳了还是没看 | `agent.steer` 只保证消息进了信箱，「它读到没有」是另一件事，面板从没追过 | 记 `pendingSteers`，等它自己的日志里出现带模板前缀的那句话才转 `read`；十分钟没读到就转 `stale` 并如实说「还没读到」——用户自己重复同样的话不算读到 |
| **总览只是碎片**：一串「版本整理好了」「那一步没做成」，**读起来没头没尾**（用户原话：可读性极差） | 根因在结构不在措辞：`recordRequest()` 在用户开口时把上一件事**整个丢掉**，43 件事只剩最后 1 件活着；每条战报都是无主句，不说是哪件事、那件事成没成 | 新增 `history`（最多 60 件，`snapRequest` 逐字段冻结，不和时间线共享数组）+ `buildChronicle()`：每件事一章，头是请求原话、腰是压缩动作、尾是结论；进行中的也占一章 |
| 做完了、验证也全过，结局却说**「你换下一件事了，这件就先停在这」** | `endingOf()` 只看 `closedBy=superseded`，不看这件事本身成没成 —— 把成功写成半途而废 | 结局语先看状态：`done/verified/done-nothing` 直接留空（完整收尾不需要解释），只有真没走完才说没走完 |
| 改了文件、跑验证挂了，却说**「做完了但改完没再跑过验证」** | `readRequest` 的 `done` 分支没区分「验证失败」，把「验了没过」和「压根没验」并成一档 | 新增 `done-blocked`：`broken && !verified` 时单独报「收了尾，但最后一次验证没过」；`open`/`tally` 同步 |
| 历史章节明明**验证全过**，却被读成**「没验过」** | `buildRequest` 用的是全局 `state.lastRun`，它会被下一件事覆盖 | 每件事自带 `request.lastRun`，`snapRequest` 一起冻结；`readRequest` 优先用它，全局的只在冷启动兜底 |
| 一场 43 件，标题写「43 件」，下面**只列 1 条** | `total` 取 `requestCount`（日志里真数到 43），但回放窗口只覆盖很晚一段，历史攒不出 43 章 —— 拿数字撑门面 | `buildChronicle` 同时给 `total` 与 `unseen`，面板写「这一场一共 43 件，从这里能看到第 43 件之后的」；有断言钉住 `unseen === 42` |

## 配置项

在 `cordis.patch.yml` 里 `config:` 下写，全部有默认值：

| 键 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `showLight` | boolean | `true` | 状态灯开关。关掉后只剩三行字。 |
| `expandDetails` | boolean | `false` | 详情默认展开。默认收起（非目标里说了不许默认展开）。 |
| `explainProvider` | string | `''` | 「问解释助手」用的 provider。空=用主 agent 的默认模型。 |
| `explainModel` | string | `''` | 同上，model。 |
| `steerTemplate` | string | `'【侧边栏提醒】{text}'` | 提醒注入前的包装模板，`{text}` 会被替换。 |
| `emptyState` | string | `''` | 空闲文案模板，支持 `{duration}` 和 `{files}`。空=用内置句式。 |

```yaml
- insert:
    - id: sidekick-lens
      name: 'dsh-sidekick-lens'
      config:
        showLight: true
        expandDetails: false
        steerTemplate: '【侧边栏提醒】{text}'
```

配置校验**永不抛异常**：非法值一律回落默认，坏了不会拖垮启动。

## 已知限制

1. **只在有会话的侧栏里出现**。没打开会话时，tab 显示「还没有选中会话」。
2. **冷启动靠事件重放**。插件加载时先问活着的 agent 状态，再从 `session.snapshotEvents()` 重放最后 400 条事件；
   会话没挂着就回读持久日志（`sessionQuery.readSession`）。更早的历史不在面板里。
3. **「下一步」是推断，不是承诺**。它来自待办清单，或从上一步的动作推出来。真实下一步由主 agent 决定。
4. **红绿之间有灰区**。报错后主 agent 常常自己重试成功；灯会先红，重试通过才转绿。
5. **解释助手看不到原因，只看到摘要**。它拿的是剥掉工具名和路径的步骤摘要——这是有意的，代价是它不知道具体文件名。
6. **`steer` 依赖下个 step 边界**。如果 agent 正卡在一个特别长的工具调用里，提醒要等它跑完才生效。想立刻停就是「先停一下」。
7. **不做历史回放 UI**。只反映当前会话正在发生的事。
8. **`stop` 只对挂着的会话有效**。会话已经落盘但仍活着时能停；彻底不在进程里的会话会回「没有可停的步骤」。
9. **`?token=` 不会落盘**。GUI 的登录令牌由 Host 进程用 WeakMap 持有，只在启动时打印一次；重启进程就换新的。
   想重新拿到，得看 `dsh web` 的启动输出，或者临时挂个只读插件调 `connection.authenticatedUrl()`。
10. **`stop` 对正在跑的一轮只验证过一次**。用一个会数到 30 的子会话做的：返回
    「已经做完的 30 步都留着 / 停掉的是：在想下一步做什么」，日志里那一轮确实中止了。
11. **总账只算它看见的那一段**。计数来自本进程观察/重放的最近 400 条事件，不是整份历史账；
    插件重载后重新开始计数。所以「改了 4 个文件」是「这段里」，不是「有史以来」。
12. **总账的「文件」是文件名的口语化叫法**，不是路径。同一目录下的同名文件会被并成一项。
13. **五条 HTTP 路由不在 DSH 的访问检查之内**。它们由 DSH 的 web server 提供，但 `/__sidekick_lens/*` 是本插件自己的路径，DSH 不为它验证登录 cookie。已加同源守卫：带了外站 `Origin`、或 `Sec-Fetch-Site: cross-site` 的请求一律拒掉（`view` 与三个门返回 `ok:false` 的一句人话，`stream` 返回 403）。不带这两个头的请求（本机脚本、curl、测试）放行——守卫防的是「浏览器里另一个页面」，不是身份认证；能这台机器上跑代码的人本来就能直接跟 Host 说话。
14. **战况只留最近 200 条**。它是「回看刚才」，不是档案馆；滑出窗口的条数会如实写在展开态底部。真需要全量历史，那是会话日志的活。
15. **部队编制只展开一层**。小队自己还有小队时只显示「它还带着 N 支」，不递归——176px 的栏里递归树是噪音，不是总览。要看孙队，进它自己的会话看。
16. **子队靠 `session.header.parentSession` 认亲**。宿主在 `subagent/start` 里不给父会话 id，所以父子关系是从子会话自己的持久元数据读的——好处是哪边的日志先到都不影响，代价是这个字段缺失时（例如非 subagent 途径建出来的旁路会话）它就不会出现在树里。
17. **提醒回执靠文本匹配**。宿主不回传 `sidekick-` 那个 id，所以只能在它日志里找带模板前缀的那句原话。改过 `steerTemplate` 之后，旧的待确认条目可能再也匹配不上，最后按 `stale` 如实说「还没读到」——不会假装成功。

## 设计取舍

**思维链进摘要，但不进「已观察到」。** 一开始只把思考拿来做心跳（思考也算在动，否则静默分不清是停住还是在想），内容丢掉。结果摘要只能靠工具名和少量最终发言拼，「它在翻文件」后面的理由全靠猜——实测这个会话里 1107 条消息带思考块，全部没被用上。现在思考会折进摘要的【仅据汇报】段，也会在还没有工具调用时接管「正在做」和「下一步」：`在想下一步做什么` 换成它真实的打算。但思考永远不标 `已观察到`，因为它只是它对自己说的话，没有任何工具证据。英文的思考不会进面板（面板只有中文），但解释助手能读到。

- **三行，不是三屏**：侧栏可能和 diff/终端共享宽度，文案一旦长就会挤到别人，所以主面板先做减法，详情按需展开。
- **不用百分比**：百分比在 agent 工作里是假的，没人知道总共几步。「第 3 / 7 步」也别当真，它只是位置感。
- **来源标注不可关**：这是产品的一部分，不是装饰。已观察到和仅据汇报混在一起，用户就没法判断该不该信。
- **三条通道在视觉上分开**：一个输入框让用户猜「我这句话会打断它吗」是最糟的设计。
- **解释助手拿的是摘要，不是会话**：它看不到工具名和路径（故意的），代价是它不知道具体文件名。但摘要分两段标注来源，所以它不会把 agent 的自吹当事实。
- **视觉上做了减法**：试过仪器网格、星野、反应堆核心、扫描带、频道号——在 176–284px 的侧栏里全部读起来像噪音。
  最后留下的是一个强调色、发丝线、两处真动画。**装饰越少，三行字越显眼**，这正是这个插件要的东西。
